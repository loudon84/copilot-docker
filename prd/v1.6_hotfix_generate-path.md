# PRD：Copilot Docker 容器 Agent 文档产物归类与路径治理方案

## 1. 文档信息

项目名称：Copilot Docker / Hermes Agent WebUI Container Kit
需求名称：容器 Agent 生成文档自动归类与路径治理
适用范围：所有通过 `copilot-docker` 创建的 Hermes 容器实例，包括 writer、finance、research、coding、sales、default 以及后续新增专家实例
优先级：P0
目标版本：v1.2 Document Routing
负责人：AI 平台 / Agent 运维工具组

## 2. 背景

当前 `copilot-docker` 已经支持多容器 Agent 实例部署，每个实例拥有独立的 `/data/hermes` 数据根目录，并包含 workspace、obsidian-vault、skills、memories、sessions 等子目录。

但实际使用中出现以下问题：

1. Agent 会把 Python 脚本、Word 生成脚本、Markdown 报告、中间文件、最终导出文件混写到 Obsidian 目录。
2. Writer 专家规则把“资料”和“生成报告”都指向 Obsidian，导致 Obsidian 同时承担知识库、工作区、导出区、脚本区四种职责。
3. `create-instance.sh` 与 `inject-expert.sh` 初始化目录不一致，后续注入专家后可能丢失部分目录约定。
4. `config.yaml` 和 runtime patch 只注册了 `obsidian_vault` MCP，没有注册 workspace MCP，Agent 工具层更容易访问 Obsidian 而不是 workspace。
5. 缺少统一的“文件类型 → 目标目录”路由规则，导致不同 Agent、不同模型、不同 prompt 产生不一致行为。

## 3. 产品目标

建立一套对所有容器 Agent 生效的“文档产物归类系统”，让 Agent 在生成任何文件前都能明确判断：

1. 这个文件是资料、草稿、中间文件、脚本、最终导出、知识沉淀，还是审计记录。
2. 这个文件应该写入 workspace、obsidian-vault、skills、artifacts、exports、scripts 中的哪个目录。
3. 哪些文件禁止写入 Obsidian。
4. 哪些文件可以进入 Obsidian 作为长期知识。
5. 新建实例、注入专家、运行时配置修补、技能安装后，目录规则保持一致。

## 4. 非目标

本期不做以下事项：

1. 不重构 Hermes Agent 核心源码。
2. 不改造 Hermes WebUI 前端文件树大结构。
3. 不把 Obsidian GUI 打包进容器。
4. 不改变现有 `/data/hermes` 作为实例数据根的设计。
5. 不把所有文件都强制迁移到数据库或对象存储。
6. 不引入复杂权限系统，只做目录契约、提示词约束、MCP 暴露、脚本校验和运行时审计。

## 5. 核心原则

### 5.1 Workspace 是工作区

`/data/hermes/workspace` 用于所有工作过程文件、临时处理文件、草稿、脚本、最终导出文件。

### 5.2 Obsidian 是长期知识库

`/data/hermes/obsidian-vault` 只保存长期可阅读、可检索、可沉淀的 Markdown 知识内容，不保存可执行脚本、临时文件、二进制导出文件。

### 5.3 Skills 是能力资产

`/data/hermes/skills` 只保存 Hermes skill，不保存普通业务报告、脚本草稿或用户导出文档。

### 5.4 Exports 是最终交付区

所有 `.docx`、`.pdf`、`.xlsx`、`.pptx`、`.html` 等面向用户交付的最终文件，默认进入 `/data/hermes/workspace/exports`。

### 5.5 Scripts 是工具脚本区

Agent 生成的 `.py`、`.sh`、`.js`、`.ts`、`.mjs`、`.ps1` 等可执行辅助脚本，默认进入 `/data/hermes/workspace/scripts`。

### 5.6 Materials 是原始资料区

用户上传或外部下载的原始资料，进入 `/data/hermes/workspace/materials`。

### 5.7 References 是解析引用区

从 PDF、网页、Excel、邮件、接口返回中抽取出来的引用材料，进入 `/data/hermes/workspace/references`。

### 5.8 Drafts 是草稿区

尚未定稿的 Markdown、文本、提纲、方案草稿，进入 `/data/hermes/workspace/drafts`。

### 5.9 Artifacts 是交互产物区

HTML UI、图表 JSON、Mermaid、Excalidraw、页面原型、可视化中间产物，进入 `/data/hermes/workspace/artifacts`。

### 5.10 Reports 是知识化报告区

已经完成审核、适合沉淀为长期知识的 Markdown 报告，可复制或生成到 Obsidian 对应目录。

## 7. 文件路由规则

| 文件类型                | 示例                               | 默认目录                                     |
| ------------------- | -------------------------------- | ---------------------------------------- |
| 原始上传资料              | PDF、Word、Excel、图片、邮件附件           | `/data/hermes/workspace/materials`       |
| 外部下载资料              | 网页保存、接口返回、公开资料                   | `/data/hermes/workspace/materials`       |
| 抽取后的引用材料            | 规格书摘要、网页摘要、OCR 文本                | `/data/hermes/workspace/references`      |
| 草稿                  | 提纲、PRD 草稿、文章草稿                   | `/data/hermes/workspace/drafts`          |
| 中间 Markdown 报告      | 未审核技术文章、评测报告                     | `/data/hermes/workspace/reports`         |
| 最终交付文档              | `.docx`、`.pdf`、`.xlsx`、`.pptx`   | `/data/hermes/workspace/exports`         |
| HTML/图表/UI artifact | `.html`、`.svg`、`.json`、`.mmd`    | `/data/hermes/workspace/artifacts`       |
| 生成脚本                | `.py`、`.sh`、`.js`、`.ts`、`.ps1`   | `/data/hermes/workspace/scripts`         |
| 临时文件                | cache、tmp、转换中间件                  | `/data/hermes/workspace/tmp`             |
| 运行态文件               | run log、job state、pipeline state | `/data/hermes/workspace/runtime`         |
| 可长期阅读知识             | 审核后的 Markdown 知识                 | `/data/hermes/obsidian-vault/<category>` |
| Hermes skill        | `SKILL.md`、skill scripts         | `/data/hermes/skills/<category>/<skill>` |

## 8. Obsidian 写入限制

默认禁止以下文件写入 `/data/hermes/obsidian-vault`：

```text
.py
.sh
.js
.ts
.mjs
.cjs
.ps1
.exe
.bin
.zip
.tar
.gz
.docx
.pdf
.xlsx
.pptx
.tmp
.cache
.log
```

允许进入 Obsidian 的文件类型：

```text
.md
.txt
.yaml
.yml
.json
.csv
```

其中 `.json`、`.csv` 仅允许作为知识索引、结构化摘要、参数表、引用清单，不允许作为运行态缓存。

## 9. 产品功能需求

### FR-1：新增统一文档路由策略文件

新增文件：

```text
expert-templates/base/policies/document-routing.yaml
```

内容包含：

1. 标准目录列表。
2. 文件扩展名分类。
3. 专家类型默认目录。
4. Obsidian 禁止扩展名。
5. 最终导出文件规则。
6. 脚本文件规则。
7. IC 产品规格书特殊规则。
8. 财务审计报告特殊规则。

### FR-2：新增 Agent 可读路径契约

新增文件：

```text
expert-templates/base/workspace/AGENTS.md
```

内容必须明确：

1. 所有文件操作必须先判断文件类别。
2. 可执行脚本不得写入 Obsidian。
3. 最终导出文件必须写入 workspace/exports。
4. 草稿写入 workspace/drafts。
5. 原始资料写入 workspace/materials。
6. 只有审核后的 Markdown 知识才能进入 obsidian-vault。
7. 每次生成多个文件时，需要在回复中列出文件路径和用途。

### FR-3：修改 Base SOUL

修改：

```text
expert-templates/base/SOUL.md
```

新增“Document Routing Rules”段落，明确 workspace、obsidian-vault、skills、exports、scripts 的职责边界。

### FR-4：修改 Writer SOUL

修改：

```text
expert-templates/writer/SOUL.md
```

把当前“source materials and generated reports in obsidian-vault”改为：

1. 原始资料进入 workspace/materials。
2. 草稿进入 workspace/drafts。
3. 未审核报告进入 workspace/reports。
4. 最终 docx/pdf/xlsx/pptx 进入 workspace/exports。
5. IC 产品长期 Markdown 知识进入 obsidian-vault/80-Product-Spec。
6. 生成脚本进入 workspace/scripts。

### FR-5：修改 Finance SOUL

修改：

```text
expert-templates/finance/SOUL.md
```

规则调整为：

1. 财务原始资料进入 workspace/materials/finance。
2. 财务分析草稿进入 workspace/drafts/finance。
3. 财务审计 Markdown 报告进入 workspace/reports/finance。
4. 审核后可归档版本进入 obsidian-vault/60-Reports。
5. 最终导出文件进入 workspace/exports/finance。
6. 禁止将凭证、密钥、敏感原始数据写入 Obsidian。

### FR-6：统一实例初始化目录

修改：

```text
scripts/create-instance.sh
scripts/inject-expert.sh
```

两者必须调用同一个公共目录初始化脚本，避免目录漂移。

新增：

```text
scripts/lib/init_hermes_dirs.sh
```

该脚本负责创建标准目录，并可被 create-instance、inject-expert、repair-instance 调用。

### FR-7：新增 workspace MCP

修改：

```text
expert-templates/base/config.yaml
scripts/lib/patch_config_runtime.py
```

在 `mcp_servers` 下新增：

```yaml
workspace:
  command: "npx"
  args:
    - "-y"
    - "@modelcontextprotocol/server-filesystem"
    - "/data/hermes/workspace"
  enabled: true
  tools:
    resources: true
    prompts: false
```

保留 `obsidian_vault`，但要让 workspace 与 obsidian-vault 同等可见。

### FR-8：新增文档路由 Skill

新增本地 skill：

```text
/data/hermes/skills/system/document-output-router/SKILL.md
```

该 skill 描述：

1. 在生成文件前必须先分类。
2. 按扩展名、用途、审核状态选择目录。
3. 对多文件输出生成 manifest。
4. 输出文件列表时必须包含：文件路径、文件类型、用途、是否最终交付、是否需要归档到 Obsidian。

该 skill 由 `install-blound-skills.sh` 自动安装到所有实例。

### FR-9：新增 manifest 机制

每次 Agent 生成一组文件时，建议生成：

```text
/data/hermes/workspace/artifacts/<task-name>.manifest.json
```

manifest 字段：

```json
{
  "task": "string",
  "profile": "writer",
  "created_at": "ISO8601",
  "files": [
    {
      "path": "/data/hermes/workspace/exports/example.docx",
      "kind": "final_export",
      "format": "docx",
      "purpose": "用户最终交付文档",
      "source": [],
      "obsidian_archive": false
    }
  ]
}
```

### FR-10：新增路由校验脚本

新增：

```text
scripts/lib/validate_document_routes.py
scripts/check-document-routes.sh
```

功能：

1. 扫描指定实例 `/data/hermes`。
2. 检查 Obsidian 内是否出现禁止扩展名。
3. 检查 workspace/exports 是否包含最终导出文件。
4. 检查 workspace/scripts 是否包含脚本文件。
5. 输出违规列表。
6. 支持 `--fix` 自动迁移明显错误文件。

### FR-11：新增实例修复脚本

新增：

```text
scripts/repair-document-routes.sh
```

用法：

```bash
bash scripts/repair-document-routes.sh writer
bash scripts/repair-document-routes.sh finance --fix
```

功能：

1. 创建缺失目录。
2. 修复权限。
3. 检查 config.yaml 是否包含 workspace MCP。
4. 检查 SOUL.md 是否包含 Document Routing Rules。
5. 扫描 Obsidian 中错误的脚本和导出文件。
6. 可选迁移到 workspace/scripts 或 workspace/exports。

### FR-12：WebUI 展示约定

本期不改 WebUI 前端，但在文档中约定：

1. 用户最终下载文件优先从 workspace/exports 获取。
2. 工作过程文件在 workspace/drafts、workspace/reports、workspace/artifacts 中查看。
3. Obsidian 只作为知识库目录，不作为默认导出目录。

## 10. 技术实现方案

### 10.1 新增公共目录初始化脚本

新增：

```bash
scripts/lib/init_hermes_dirs.sh
```

核心参数：

```bash
init_hermes_dirs "$DATA_DIR"
```

被以下脚本调用：

```text
scripts/create-instance.sh
scripts/inject-expert.sh
scripts/repair-document-routes.sh
```

### 10.2 修改 runtime patch

`patch_config_runtime.py` 的 `runtime_patch()` 新增 workspace MCP，并保留 obsidian_vault MCP。

### 10.3 修改专家模板

需要修改：

```text
expert-templates/base/SOUL.md
expert-templates/writer/SOUL.md
expert-templates/finance/SOUL.md
```

所有专家模板必须继承 base 的路径治理规则，专家只能增加特定业务目录，不能覆盖基本规则。

### 10.4 修改 install-blound-skills

在本地 skill 安装段新增：

```text
system/document-output-router
```

并确保该 skill 不覆盖用户已有同名 skill，除非使用 `--force-local` 参数。

### 10.5 新增校验脚本

`validate_document_routes.py` 负责纯检查，`check-document-routes.sh` 负责实例级封装。

检查项：

1. 目录完整性。
2. Obsidian 禁止扩展名。
3. workspace 最终导出文件归位。
4. scripts 文件归位。
5. skills 目录只包含 skill 结构。
6. manifest 是否有效。

## 11. 关键用户故事

### US-1：Writer 生成 Word 报告

作为业务写作 Agent，当用户要求生成 Word 报告时，Agent 应该：

1. 把资料放入 workspace/materials。
2. 把草稿 Markdown 放入 workspace/drafts 或 workspace/reports。
3. 把 `generate-docx.py` 放入 workspace/scripts。
4. 把最终 `.docx` 放入 workspace/exports。
5. 只有最终 Markdown 知识摘要进入 obsidian-vault/80-Product-Spec。

### US-2：Finance 生成资金日报

作为财务 Agent，当用户要求生成资金日报时，Agent 应该：

1. 把原始数据放入 workspace/materials/finance。
2. 把分析过程文件放入 workspace/reports/finance。
3. 把最终 `.xlsx` 或 `.pdf` 放入 workspace/exports/finance。
4. 把审核后的 Markdown 摘要归档到 obsidian-vault/60-Reports。
5. 不把敏感原始明细写入 Obsidian。

### US-3：运营同事创建 Skill

作为运营同事，当他要求 Agent 创建新 skill 时，Agent 应该：

1. 把 skill 写入 `/data/hermes/skills/<category>/<skill-name>`。
2. 把 skill 测试脚本写入 skill 自身的 `scripts/`。
3. 不把 skill 文件写入 workspace 或 Obsidian。
4. 生成 skill 说明文档时，可把可读介绍归档到 obsidian-vault/40-Skills。

## 12. 验收标准

### AC-1：新建实例目录完整

执行：

```bash
bash scripts/create-instance.sh writer 9601 writer
```

必须生成完整标准目录。

### AC-2：注入专家后目录不漂移

执行：

```bash
bash scripts/inject-expert.sh writer writer
```

不得删除或遗漏 workspace/scripts、workspace/reports、workspace/runtime、workspace/tmp、workspace/artifacts、obsidian-vault/80-Product-Spec。

### AC-3：config.yaml 包含 workspace MCP

执行：

```bash
bash scripts/patch-config-runtime.sh writer
```

生成的 config.yaml 必须包含：

```yaml
mcp_servers:
  workspace:
  obsidian_vault:
  gbrain:
```

### AC-4：Writer 不再把脚本写入 Obsidian

让 writer 生成 Word 报告时，`.py` 脚本必须位于：

```text
/data/hermes/workspace/scripts
```

不得位于：

```text
/data/hermes/obsidian-vault
```

### AC-5：最终文件进入 exports

`.docx`、`.pdf`、`.xlsx`、`.pptx` 默认必须进入：

```text
/data/hermes/workspace/exports
```

### AC-6：Obsidian 禁止扩展名检查通过

执行：

```bash
bash scripts/check-document-routes.sh writer
```

不得在 Obsidian 中发现 `.py`、`.sh`、`.docx`、`.pdf`、`.xlsx` 等违规文件。

### AC-7：所有实例可批量检查

支持：

```bash
bash scripts/check-document-routes.sh --all
```

输出所有实例的检查结果。

## 14. 风险与对策

### 风险 1：模型仍然忽略规则

对策：把规则同时写入 base SOUL、workspace AGENTS、document-output-router skill 和 policies/document-routing.yaml，多层约束。

### 风险 2：已有实例配置不会自动更新

对策：提供 `repair-document-routes.sh --all`，批量修复目录、config、权限和路由策略。

### 风险 3：误迁移历史文件

对策：`--fix` 默认只迁移明显错误扩展名；所有迁移前先生成 manifest 和 backup。

### 风险 4：Obsidian 中已有 docx/pdf 被业务引用

对策：迁移时保留同名 `.md` 索引文件，记录原路径、新路径、迁移时间和用途。

## 16. 最终效果

完成后，所有容器 Agent 都遵循统一路径规则：

1. 工作过程进入 workspace。
2. 最终交付进入 workspace/exports。
3. 脚本进入 workspace/scripts。
4. 原始资料进入 workspace/materials。
5. 引用资料进入 workspace/references。
6. 长期知识进入 obsidian-vault。
7. skill 进入 skills。
8. 任何违规文件可被检查脚本发现并修复。

该方案将把“Agent 自行猜路径”升级为“容器级文档产物治理能力”，适用于后续所有专业 Agent 实例。
