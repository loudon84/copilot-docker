## 1. 项目背景

`hermes-sqlbot-adapter` 用于将 Hermes 的财务问数工具连接到 SQLBot MCP 服务。当前 SQLBot MCP 直连链路已经完成验证：登录、工作空间、数据源选择、SQL 生成、SQL 执行及结构化数据返回均正常。

当前工作只修复和优化 Adapter，不修改 SQLBot 镜像及 SQLBot 内部源码。

已验证的 SQLBot MCP 成功结果如下：

```json
{
  "success": true,
  "record_id": 60,
  "title": "交易凭证101IN26070194销售利",
  "sql": "SELECT ...",
  "data": {
    "fields": ["detail_id", "ar_trx_number"],
    "data": [
      {
        "detail_id": 28799177.0,
        "ar_trx_number": "101IN26070194"
      }
    ]
  }
}
```

Adapter 的目标是把上述 SQLBot 原始协议转换为稳定的 Hermes `finance-bi` 工具协议，并负责会话隔离、错误分类、结果治理、审计和运行可靠性。

## 2. 产品边界

### 2.1 Adapter 负责

1. Hermes Tool 参数解析和运行上下文提取。
2. SQLBot MCP 工具参数适配。
3. SQLBot 登录 Token、`chat_id` 和 Hermes Session 映射。
4. `ask`、`followup`、`explain`、`reset` 工具编排。
5. SQLBot 返回结构解析和标准化。
6. 查询提交前的问题级保护。
7. SQLBot 执行后的 SQL 与结果校验。
8. Token 加密存储、会话过期处理和查询审计。
9. 超时、网络错误和协议错误分类。
10. 插件目录加载和 Python 包安装两种部署方式。

### 2.2 Adapter 不负责

1. 不自行生成 SQL。
2. 不直接连接业务数据库执行 SQL。
3. 不替代 SQLBot 的术语、字段描述和 SQL 示例管理。
4. 不修改 SQLBot 镜像或内部代码。
5. 不承诺在 SQLBot 执行前拦截生成 SQL；当前 MCP `mcp_question` 是生成和执行一体化接口。
6. 不向模型暴露 SQLBot 用户名、密码、Token、`chat_id`、工作空间 ID 或数据源 ID。

## 3. 当前源码审计结论

当前源码约 2,700 行，模块划分方向基本正确，但存在多项阻断生产使用的问题。

### 3.1 P0 阻断问题

| 编号 | 问题 | 当前表现 | 影响 |
|---|---|---|---|
| P0-01 | MCP 参数名与已验证协议不一致 | Adapter 发送 `access_token`、`workspace_id`、`response_mode`；实际链路使用 `token`、`oid`、`stream`、`lang`、`return_img` | 工具调用失败或参数被忽略 |
| P0-02 | 成功结果解析不兼容 | 当前解析器未读取顶层 `sql/title/record_id`，也未读取 `data.data` 行数据 | SQL 为空、标题为空、结果行数为 0 |
| P0-03 | Hermes Tool Handler 签名不兼容 | 当前 handler 直接声明 `question` 等业务参数，没有接收 `params: dict` | Registry 以参数字典调用时产生类型错误 |
| P0-04 | Hermes 运行上下文被丢弃 | handler 将运行时 `**kwargs` 全部忽略，Service 未收到 `session_id` | 所有用户可能共享 `cli-session/local-cli` |
| P0-05 | `finance_bi_ask` 复用旧 `chat_id` | 新问题继续使用已有 SQLBot 对话 | 不相关问题发生上下文污染 |
| P0-06 | Wheel 缺少全部子包 | `pyproject.toml` 只打包 `sqlbot_adapter` 顶层；实际构建的 wheel 不含 `client/security/session/...` | Pip 安装后运行即报导入错误 |

### 3.2 P1 高优先级问题

| 编号 | 问题 | 影响 |
|---|---|---|
| P1-01 | `CallToolResult.isError` 未检查 | MCP Tool Error 可能被当成空成功结果 |
| P1-02 | 请求超时仅发生在同步等待层 | Future 超时后后台协程仍可能继续运行，形成幽灵查询 |
| P1-03 | `verify_ssl`、连接超时配置未实际生效 | 配置与行为不一致 |
| P1-04 | `token_expires_at` 已存储但从未检查 | 过期 Token 被继续复用 |
| P1-05 | 没有认证失效恢复策略 | Token 失效后只能返回通用错误 |
| P1-06 | 未知 `datasource_key` 静默回退默认数据源 | 查询可能落到错误数据域 |
| P1-07 | 业务编号提取规则不完整 | “交易凭证编号 101IN...”和“应收交易编号”无法识别 |
| P1-08 | 标识符校验只检查 SQL 字符串包含值 | 值出现在 SELECT、注释或无关表达式也可能通过 |
| P1-09 | SQL 解析未指定 SQL Server 方言 | `[]`、`TOP`、T-SQL CTE 等可能误判 |
| P1-10 | 未禁止 SQL Server `SELECT INTO` | 只读保护存在缺口 |
| P1-11 | 明细过滤检查发生在 SQLBot 执行后 | 无法阻止无过滤明细查询提交 |
| P1-12 | SQLite 只有建表，没有真实 Schema Migration | 旧库升级后缺字段，`upsert` 失败 |
| P1-13 | 同一 Hermes Session 没有串行锁 | 并发 ask/followup 会覆盖 `chat_id` 和上下文顺序 |
| P1-14 | `explain(query_id)` 只能解释最近一次查询 | 已有查询历史表未被利用 |
| P1-15 | `data_and_summary` 默认同时返回 chart | 返回体无谓增大 |

### 3.3 P2 工程问题

1. `tests/` 为空，没有单元测试和协议回归测试。
2. README 声称存在 `--deep`，实际脚本没有该参数。
3. ZIP 包含 `__pycache__` 和 `.pyc`。
4. 配置整数未校验，错误环境变量会导致运行时直接崩溃。
5. 审计文件没有权限收敛、保留期和并发写保护。
6. SQLite 查询历史没有清理机制。
7. 单例 Service 初始化没有线程锁。

## 4. 改造目标

### 4.1 功能目标

1. Hermes 可稳定调用 SQLBot 完成首轮问数和连续追问。
2. 新的 `finance_bi_ask` 必须创建独立 SQLBot 对话。
3. `finance_bi_followup` 只复用同一 Hermes Session 的当前 SQLBot 对话。
4. 不同 Hermes Session 之间不得共享 Token、`chat_id` 或查询上下文。
5. 正确解析当前 SQLBot 成功和失败返回格式。
6. 向 Hermes 返回稳定、可测试、无敏感信息的统一 JSON。
7. 对无过滤明细问题在提交 SQLBot 前阻断。
8. 对返回 SQL 做只读、字段过滤和业务编号保留校验。
9. 支持目录插件和 Pip Wheel 两种安装方式。

### 4.2 可靠性目标

1. 单次问数超时可控，超时后请求必须被取消。
2. 问数请求不得自动重放，避免重复执行。
3. 登录和 MCP 初始化可对纯传输错误重试一次。
4. 同一 Hermes Session 的问数操作串行执行。
5. Session Store 支持 v2 到 v3 的幂等迁移。
6. 关键协议和安全逻辑具备自动化测试。

### 4.3 安全目标

1. SQLBot 密码、Token、`chat_id` 和加密密钥不进入模型返回。
2. Token 只以 Fernet 密文落盘。
3. SQLBot 业务数据库账号必须为只读账号。
4. Adapter 的 SQL Guard 明确定义为“执行后校验”，不得描述为数据库执行防火墙。
5. 审计文件权限为 `0600`，目录权限为 `0700`。

## 6. 工具定义

### 6.1 `finance_bi_ask`

用途：发起一个新的独立问数。

输入：

```json
{
  "question": "查询销售利润报表交易凭证编号101IN26070194的数据",
  "datasource_key": "sales_profit",
  "response_mode": "data_and_summary"
}
```

行为：

1. 校验问题和数据源别名。
2. 执行问题级预检。
3. 调用 `mcp_start` 创建新 Token 和新 `chat_id`。
4. 覆盖当前 Hermes Session 的 SQLBot 会话映射。
5. 调用 `mcp_question`。
6. 解析、校验、标准化并保存查询上下文。

禁止复用旧 `chat_id`。

### 6.2 `finance_bi_followup`

用途：继续当前 Hermes Session 的 SQLBot 对话。

要求：

1. 必须存在有效 Session 映射。
2. 必须存在未过期 Token 和 `chat_id`。
3. 同一 Session 的 followup 必须串行。
4. Token 已失效时返回 `SQLBOT_SESSION_EXPIRED`，不自动创建新对话伪装为追问。

### 6.3 `finance_bi_explain`

用途：解释本地已记录的查询，不重新访问 SQLBot 和数据库。

支持：

1. 不传 `query_id`：解释当前 Session 最近一次查询。
2. 传 `query_id`：读取当前用户、当前 Session 范围内的历史记录。
3. 返回 SQL、业务问题、过滤条件、字段、行数、截断状态和上游 `record_id`。
4. 不返回结果明细行。

### 6.4 `finance_bi_reset`

用途：删除当前 Hermes Session 对应的 SQLBot 映射。

行为：

1. 删除 Token、`chat_id` 和最后查询上下文。
2. 保留查询审计历史。
3. 下一次 `ask` 新建 SQLBot 对话。

## 7. Hermes Handler 兼容层

当前 handler 必须统一改为兼容参数字典和运行时参数：

```python
def finance_bi_ask(params: dict | None = None, **runtime_kwargs) -> str:
    payload = normalize_handler_params(params, runtime_kwargs)
    runtime_ctx = runtime_context_provider.resolve(runtime_kwargs)
    return json_ok(
        get_service().ask(
            payload["question"],
            datasource_key=payload.get("datasource_key", ""),
            response_mode=payload.get("response_mode", "data_and_summary"),
            hermes_ctx=runtime_ctx,
        )
    )
```

兼容规则：

1. 第一个位置参数是字典时，从字典读取 Tool 参数。
2. 兼容测试脚本直接使用关键字参数调用。
3. `session_id`、`task_id`、`tool_call_id` 等运行时字段不得混入业务参数。
4. 运行时上下文必须显式传入 Service。
5. `reset` 也必须接收 `params`，即使其为空字典。

## 8. 运行上下文与会话隔离

### 8.1 上下文提取优先级

1. Hermes Registry 运行时 kwargs。
2. 显式注入的 `RuntimeContext`。
3. CLI 测试环境变量。

### 8.2 强制规则

1. Gateway 模式必须取得 `session_id`。
2. 不允许 Gateway 回退到固定值 `cli-session`。
3. 无 `user_id` 时使用当前 `session_id` 生成隔离标识，禁止使用共享 `local-cli`。
4. CLI 模式必须显式设置 `SQLBOT_CLI_SESSION_ID`；不得使用固定默认值。
5. Session 主键继续使用：

```text
profile_name + hermes_session_id + hermes_user_id
```

### 8.3 并发控制

新增 `SessionLockManager`：

```text
lock key = profile_name / hermes_session_id / hermes_user_id
```

锁覆盖范围：

1. `mcp_start`。
2. `mcp_question`。
3. Session Store 更新。
4. followup 顺序提交。

首版使用进程内 `threading.RLock`。部署多进程或多副本时切换 Redis/数据库租约锁；在此之前固定 Adapter 单进程运行。

### 9.1 固定工具名称

```python

mcp_ws_list
mcp_datasource_list
```

```json
{
  "username": "...",

```

#### `mcp_ws_list`

```json
{
  "token": "..."
}
```

#### `mcp_datasource_list`

```json
{

```

```json
{
```

| `chart` | `return_img=true` | rows + chart，summary 可选 |

`data_and_summary` 不再默认返回 chart。

## 10. MCP Client 改造

### 10.1 请求超时

在协程内部使用 `asyncio.timeout()` 或 AnyIO CancelScope：

```python
async with asyncio.timeout(timeout):
    ...
```

`run_coro()` 在同步等待超时时必须：

1. 调用 `future.cancel()`。
2. 等待取消确认。
3. 返回 `SQLBOT_TRANSPORT_ERROR` 或 `SQLBOT_UNAVAILABLE`。

不得让超时请求继续在后台执行。

### 10.2 重试规则

允许重试一次：

1. MCP initialize 失败。
2. `mcp_start` 在提交前发生连接失败。
3. 工作空间和数据源列表读取发生纯传输错误。

禁止自动重试：

1. `mcp_question`。
2. 已收到 SQLBot `record_id` 的请求。
3. SQL 执行失败。
4. 安全校验失败。

### 10.3 MCP 错误检查

必须检查：

```python
result.isError
```

`isError=true` 时，不得进入成功结果解析；必须读取 content 并映射为标准错误。

### 10.4 连接配置

1. `verify_ssl` 必须接入实际 HTTP Client。
2. connect/read/write/pool timeout 分开配置。
3. 日志不得输出 Tool 参数中的 Token 和密码。

## 11. SQLBot 返回解析

### 11.1 首选成功格式

```json
{
  "success": true,
  "record_id": 60,
  "title": "...",
  "sql": "SELECT ...",
  "data": {
    "fields": ["field_a"],
    "data": [{"field_a": "value"}]
  }
}
```

解析规则：

```text
sql                = top.sql
upstream_record_id = top.record_id
 title              = top.title
columns             = top.data.fields
rows                = top.data.data
chart               = top.chart 或 top.data.chart
summary             = top.summary/answer 或 top.data.summary/answer
```

### 11.2 兼容格式

解析器还需兼容：

1. `data.columns + data.rows`
2. `columns + rows`
3. `fields + result`
4. `structuredContent`
5. MCP TextContent JSON
6. JSON Fence
7. `message` 内嵌 JSON 错误

### 11.3 失败格式

以下任一条件判定失败：

1. `isError=true`
2. `success=false`
3. `code` 非 0
4. `type=exec-sql-err`
5. `message` 或 `traceback` 包含执行错误
6. SQLBot 返回 `error`

### 11.4 成功完整性校验

成功结果至少满足：

1. `success=true`。
2. `sql` 非空。
3. `fields` 是列表。
4. `data` 是列表。
5. 每行可转换为字典。

缺少关键字段返回 `SQLBOT_RESPONSE_INVALID`，不得伪装成 0 行成功。

## 12. 查询治理

### 12.1 提交前问题级保护

新增 `preflight_question_guard()`，在调用 SQLBot 前执行：

1. 问题长度限制。
2. 明细查询必须包含精确编号、日期范围或明确业务实体。
3. 禁止用户要求修改、删除、创建表或执行存储过程。
4. `datasource_key` 必须在允许列表内。

这一步可真正阻止明显不合规问题进入 SQLBot。

### 12.2 执行后 SQL 校验

SQLBot 返回 SQL 和数据后执行：

1. 只允许单条 SELECT、CTE 或 UNION 查询。
2. 禁止 DML、DDL、EXEC、CALL、MERGE。
3. SQL Server 禁止 `SELECT INTO`。
4. 禁止跨数据库三段式、四段式对象名。
5. 禁止访问系统 Schema 和系统表。
6. 可选：限制到配置的 Schema/Table Allowlist。
7. 限制 SQL 长度和返回列数。
8. 使用 `sqlglot` 并根据数据源配置指定 `tsql` 方言。

注意：该校验发生于 SQLBot 执行后，作用是阻止不合规数据进入 Hermes，不是阻止数据库已经发生的执行。因此业务数据源必须使用只读账号。

### 12.3 业务编号保护

业务标识符改为配置驱动：

```yaml
business_identifiers:
  - names:
      - 交易凭证编号
      - 交易凭证号
      - 应收交易编号
      - 应收发票编号
      - AR发票号
    field: ar_trx_number
    match: exact
```

支持的值字符：

```text
A-Z a-z 0-9 _ - / . #
```

校验要求：

1. 问题中识别出的值必须出现在 WHERE/JOIN ON/HAVING 的谓词中。
2. `match=exact` 必须使用 `=` 或 `IN`，不得使用 `%LIKE%`。
3. 对应字段必须是配置指定字段或其表别名限定字段。
4. 仅在 SQL 字符串中出现该值不能通过校验。

## 13. 结果治理与统一返回

### 13.1 标准成功结构

```json
{
  "success": true,
  "query_id": "fbq_xxxxxxxxxxxx",
  "upstream_record_id": "60",
  "title": "交易凭证101IN26070194销售利润",
  "datasource": {
    "key": "sales_profit",
    "name": "销售利润数据源"
  },
  "query": {
    "question": "...",
    "sql": "SELECT ...",
    "filters": [],
    "row_count": 1,
    "returned_row_count": 1,
    "truncated": false
  },
  "columns": [
    {
      "name": "ar_trx_number",
      "label": "交易凭证编号",
      "type": "string"
    }
  ],
  "rows": [],
  "summary": null,
  "chart": null,
  "warnings": [],
  "meta": {
    "source": "sqlbot",
    "generated_at": "2026-07-27T20:00:00+08:00",
    "request_id": "..."
  }
}
```

### 13.2 行数限制

1. `SQLBOT_MODEL_RESULT_ROWS`：返回 Hermes 模型的行数，默认 100。
2. `SQLBOT_MAX_RESULT_ROWS`：Adapter 可接受的最大行数，默认 1000。
3. 超过模型行数：截断并返回 warning。
4. 超过硬上限：默认截断到硬上限，不再直接丢弃所有结果。
5. 增加 `SQLBOT_MAX_RESULT_BYTES`，避免超大 JSON 占用内存。

### 13.3 列数限制

新增：

```text
SQLBOT_MAX_RESULT_COLUMNS=50
```

超过上限时：

1. 优先保留 SQLBot 返回字段顺序的前 N 列。
2. 返回截断 warning。
3. 审计记录原始列数。

## 14. 错误协议

统一返回：


## 15. Session Store v3

### 15.1 Schema 变更

`sqlbot_sessions` 增加：

```text
session_version
last_upstream_record_id
last_response_mode
last_error_code
```

`sqlbot_queries` 增加：

```text
upstream_record_id
query_payload_json
title
row_count
returned_row_count
truncated
request_id
```

### 15.2 迁移机制

`init_schema()` 改为版本迁移器：

```text
v1 -> v2
v2 -> v3
```

实现要求：

1. 读取 `sqlbot_schema_meta.schema_version`。
2. 使用 `PRAGMA table_info()` 检查字段。
3. 逐版本执行 `ALTER TABLE ADD COLUMN`。
4. 单事务执行。
5. 迁移可重复运行。
6. 迁移失败不得覆盖 schema_version。

### 15.3 Token 过期

读取 Session 时同时检查：

1. Adapter Session TTL。
2. `token_expires_at`。

处理规则：

- `ask`：过期后调用 `mcp_start` 新建对话。
- `followup`：返回 `SQLBOT_SESSION_EXPIRED`，要求重新 ask。

### 15.4 数据清理

新增：

```text
SQLBOT_QUERY_RETENTION_DAYS=90
SQLBOT_AUDIT_RETENTION_DAYS=90
```

启动时和每日首次查询时执行一次轻量清理。

## 20. 验收标准

### 20.1 首轮查询

输入：

```text
查询销售利润报表交易凭证编号101IN26070194的数据
```

必须满足：

1. `success=true`
2. `query.sql` 非空
3. `rows` 至少 1 行
4. `ar_trx_number=101IN26070194`
5. `upstream_record_id` 非空
6. 不返回 Token、`chat_id` 或内部数据源 ID

### 20.2 连续追问

首轮后执行：

```text
只保留销售额、实际毛利和毛利率
```

必须使用同一 SQLBot `chat_id`，但 `chat_id` 不出现在工具返回。

### 20.3 新问题隔离

再次调用 `finance_bi_ask`：

```text
查询本月各品牌销售额
```

必须新建 SQLBot 对话，不继承上一交易凭证条件。

### 20.4 多 Session 隔离

Session A 与 Session B 并发问数：

1. Session A 的 followup 不得使用 Session B 的上下文。
2. SQLite 中必须存在两条独立 Session 记录。
3. 审计记录可通过 request_id 区分。

### 20.5 包安装

```bash
pip install hermes_sqlbot_adapter-1.12.0-py3-none-any.whl
python -c "from sqlbot_adapter.client.mcp_client import SQLBotMCPClient"
```

必须成功。
