# CEO 战略办公室 Hermes Profile 团队设计规格书

**状态：** 已批准的设计基线  
**日期：** 2026-07-14  
**目标仓库：** `loudon84/copilot-docker`  
**目标专家包：** `expert-templates/ceo-strategic-office`  
**部署模式：** 1 个 Docker 容器、1 个 root/default 首席幕僚 Profile、7 个命名 Hermes Profile、Hermes Kanban 协作平面、Agency Agents 动态专家池

> **Cursor 实施约束**  
> 本文档是本功能的唯一架构与产品基线。Cursor 在生成实施计划、修改脚本、创建模板和编写测试时，必须逐项遵守本文档。不得把 7 个永久顾问合并为一个大 Prompt，不得仅使用 `delegate_task` 替代永久 Profile 协作，也不得把每个顾问拆成独立 Docker 容器。任何偏离本文档的实现，都必须先形成变更说明并重新经过架构审批。

---

## 1. 决策摘要

CEO 战略办公室必须实现为一个 **Hermes Profile 团队包**，而不是一个包含多个角色描述的大型 Persona Prompt，也不是 8 个独立 Docker 容器。

最终部署包含：

- 1 个 Docker 容器，并复用 1 个共享 Hermes 镜像；
- 1 个 root/default Hermes Profile，CEO 通过 WebUI 和 Gateway 与其交互；
- 7 个永久命名 Hermes Profile，分别拥有独立身份、记忆、会话、Workspace、Skills 和日志；
- 1 个 Hermes Kanban Board，用于跨 Profile 的持久化任务分派、依赖管理、审计和人工介入；
- 1 个 Agency Agents Router，用于短生命周期、面向单次任务的动态专家调用；
- 1 个只读的公司共享上下文目录；
- 针对董事会、投资、法律、价格、合同、对外沟通和人事事项的明确人工审批门。

对外统一入口仍然是 root/default Profile。7 个命名 Profile 是团队内部的永久顾问，不单独暴露 WebUI 或 Gateway 端口。

---

## 2. 建设目标

1. 通过以下一条命令创建完整 CEO 团队结构：

   ```bash
   bash scripts/create-instance.sh ceo-office 9600 ceo-strategic-office
   ```

2. 保持 `writer`、`finance`、`sale` 以及其他现有单专家模板的行为不变。
3. 使用 Hermes 原生命名 Profile，目录位于 `/data/hermes/profiles/<name>`。
4. 永久 Profile 之间的跨角色持久化工作，必须通过 Hermes Kanban 协作。
5. `delegate_task` 和 Agency Agents 仅用于短生命周期动态专家任务。
6. 隔离每个永久顾问的 Hindsight Bank、会话、Workspace 与长期记忆。
7. 在不混合专业记忆的前提下，共享已经审核的公司和 CEO 背景上下文。
8. 团队创建必须具备幂等性，并且不得破坏已有实例。
9. 提供团队专用 Doctor 脚本，执行确定性结构和运行状态验证。
10. 保持 1 个 WebUI 和 1 个 API Gateway，作为 CEO 的统一交互界面。

---

## 3. 非目标范围

首期实现不包括：

- 为每个顾问创建独立容器、端口或 Gateway；
- 在 WebUI 中把命名 Profile 直接暴露给 CEO 选择；
- 允许永久顾问自动发送外部消息或作出业务承诺；
- 自动发布交易所公告、合同、价格、投资决策或法律结论；
- 赋予动态子 Agent 永久记忆或正式 Profile 身份；
- 把 Paperclip 或 Nodeskclaw 作为本功能的必选控制平面；
- 替代 EBS、CRM、财务、审计、法务或公司秘书等权威系统；
- 允许普通 Profile 工作流写入公司共享上下文目录；
- 为 CEO 实例单独修改或构建一套基础 Docker 镜像。

## 4. 当前仓库约束

当前仓库把 `create-instance.sh` 的第一个参数作为 Docker 实例标识：

```text
instances/<instance>/
container: hermes-<instance>
root Hermes home: instances/<instance>/data/hermes
```

当前 `inject-expert.sh` 会依次复制：

```text
expert-templates/base/*
expert-templates/<expert>/*
```

到同一个 root Hermes Home，因此当前只支持单 Profile 专家模板。

Docker Compose 当前只把一个宿主机目录挂载到 `/data/hermes`，启动一个 root Gateway 和一个 WebUI，并暴露一个 API Model Name。本设计不改变这个容器和端口模型，而是在 `/data/hermes` 内部创建多个 Hermes 命名 Profile。

## 5. 运行时架构

```text
CEO / 经授权的高管用户
              |
              v
Hermes WebUI + Gateway
root/default Profile：CEO Strategic Office / Chief of Staff
              |
              +---------------- Hermes Kanban ----------------+
              |                                                |
              v                                                v
永久命名顾问 Profile                                   审查门 Profile
- strategy-investment                                - strategy-red-team
- commercial-market-intelligence                     - compliance-evidence
- finance-board-governance
- operations-supply-risk
- technology-rd-ai
              |
              v
Agency Agents Router
仅在需要时加载的短生命周期动态专家
```

### 5.1 root/default Profile

root/default Profile 是唯一直接面向 CEO 的 Profile，负责：

- 用户意图和决策等级识别；
- 资料、数据源和上下文发现；
- 顾问选择；
- Kanban 任务拆解与依赖关系创建；
- 汇总顾问输出；
- 展示异议、分歧与风险；
- 生成高管决策简报；
- 记录决策并跟踪后续行动；
- 触发人工审批和升级。

root/default Profile 不得冒充 CEO，也不得代替 CEO 作出保留决策。

### 5.2 永久命名 Profile

永久 Profile 使用 Hermes Named Profile 实现，具有长期身份和记忆。它们通过 Kanban 接收任务，并可在自己的任务内部按需调用短生命周期动态专家。

### 5.3 动态专家

Agency Agents 通过 Hermes Agency Agents Router 以临时子 Agent 形式加载，用于专项研究、反方挑战、内容综合或特定领域推理。动态专家不替代永久 Profile，也不拥有永久 Profile 记忆。

## 6. 团队角色清单

### 6.1 root/default — CEO 首席幕僚

**显示名称：** CEO Strategic Office  
**角色：** Chief of Staff / CEO 战略编排者

职责：

- 保护 CEO 注意力，只呈现真正重要的问题；
- 把请求分类为信息查询、分析、建议或正式决策；
- 选择能够完成任务的最小充分顾问集合；
- 强制要求证据，并明确缺失数据；
- 保留重大分歧，不制造虚假的一致意见；
- 把专业顾问输出转换为精简决策简报；
- 记录决策、负责人、截止日期、关键假设和复盘日期；
- 挑战薄弱假设，避免迎合式结论。

### 6.2 `strategy-investment` — 战略与投资顾问

职责：

- 公司战略与业务组合战略；
- 半导体产品线组合；
- 地理区域和市场扩张；
- 投资、并购和战略合作分析；
- 资本配置与机会成本权衡；
- 分销业务与自有产品业务的平衡；
- 替代方案和不投资方案分析；
- 战略匹配度、防御能力、选择权与退出逻辑。

### 6.3 `commercial-market-intelligence` — 商业与市场情报顾问

职责：

- 半导体市场和技术需求趋势；
- 原厂与产品线情报；
- 客户集中度、增长信号和流失风险；
- 东南亚市场机会；
- 竞争对手、替代产品和渠道分析；
- 重点客户利益相关者和空白机会分析；
- 新产品线引入评估；
- 市场证据采集和置信度分级。

### 6.4 `finance-board-governance` — 财务、董事会与治理顾问

职责：

- 财务表现和利润质量；
- 现金流、库存资金占用和应收账款风险；
- 投资模型和下行情景；
- 董事会和高管经营报告；
- 香港上市公司治理敏感性识别；
- 投资者关系简报支持；
- 披露敏感事项提醒；
- 并购与战略投资财务分析。

该 Profile 只输出分析草案。正式会计、审计、披露和法律结论必须经过授权人员审核。

### 6.5 `operations-supply-risk` — 运营、供应链与风险顾问

职责：

- 跨国供应链韧性；
- 库存、短缺和呆滞减值风险；
- 原厂授权和分货风险；
- 客户信用和回款风险；
- 汇率与跨境结算风险；
- 物流、贸易和区域政策风险；
- 运营控制和异常分析；
- Oracle EBS 与内部系统的运营洞察。

### 6.6 `technology-rd-ai` — 技术、硬件研发与 AI 转型顾问

职责：

- 智能安防、智能家居和光模块产品组合；
- 硬件研发阶段门评估；
- 技术可行性和商业化准备度；
- 产品、制造和供应链依赖；
- 企业 AI、Agent、RAG 和知识平台战略；
- AI 投资价值、交付风险和组织影响；
- 把技术发现转换为资本投入、交付周期和业务成果。

### 6.7 `strategy-red-team` — 战略红队

职责：

- 攻击优选方案及其核心假设；
- 模拟原厂、客户、竞争对手、投资者、监管者和员工的反应；
- 找出隐藏替代方案和二阶影响；
- 定义最坏情景、止损触发条件和反转条件；
- 测试延期执行和不执行方案；
- 输出结构化挑战报告，而不是替代最终决策。

### 6.8 `compliance-evidence` — 合规与证据审查

职责：

- 把结论分类为事实、推断、假设或建议；
- 检查来源是否存在，数字是否一致；
- 标记无证据支持的确定性结论和数据缺口；
- 识别上市公司、隐私、财务、合同和跨境敏感事项；
- 明确必须经过财务、法务、审计或公司秘书审核的内容；
- 在证据或审批条件不满足时阻止最终定稿。

## 7. 决策等级与路由规则

| 等级 | 含义 | 最低路由要求 |
|---|---|---|
| D0 | 信息检索或摘要 | root Profile；可选动态专家 |
| D1 | 可逆的运营建议 | root + 1 个永久顾问 |
| D2 | 跨部门、预算或业务组合建议 | root + 2 个及以上永久顾问；涉及外部或敏感事项时增加合规审查 |
| D3 | 董事会、上市公司、重大投资、并购或监管事项 | root + 相关永久顾问 + 战略红队 + 合规证据审查 |
| D4 | 高度敏感的法律、人事、披露、合同或对外承诺事项 | 只提供分析；必须由授权人员作出决策和审批 |

root Profile 可以把请求升级到更高等级，但不得为了绕过审查门而降低请求等级。

## 8. 协作模型

### 8.1 永久 Profile 之间的跨角色工作

满足以下任一条件时必须使用 Hermes Kanban：

- 跨越多个永久 Profile；
- 需要任务依赖顺序；
- 需要在容器重启后继续存在；
- 需要评论或人工介入；
- 需要重试、阻塞或审计历史；
- 在会话上下文压缩后仍需可发现和可追踪。

### 8.2 短生命周期动态工作

满足以下条件时使用 `delegate_task` 和 Agency Agents：

- 任务生命周期短，结果直接返回调用方；
- 不需要永久专业记忆；
- 执行过程中不需要人工介入；
- 需要一个聚焦的专业视角；
- 结果将作为永久 Profile 或 root Profile 的输入。

### 8.3 标准决策流程

1. root Profile 接收 CEO 请求。
2. root Profile 判定决策等级。
3. root Profile 收集可用内部上下文并识别证据缺口。
4. root Profile 创建满足任务所需的最小 Kanban 顾问任务集合。
5. 相互独立的顾问任务并行执行。
6. 顾问任务完成后创建综合分析任务。
7. D3 和 D4 事项必须经过 `strategy-red-team` 与 `compliance-evidence`。
8. root Profile 生成 CEO 决策简报。
9. CEO 或经授权高管记录最终决策。
10. root Profile 记录执行负责人、截止日期、复盘日期和停止条件。

## 9. CEO 决策简报输出契约

每份正式决策简报必须包含：

1. **需要决策的事项**：明确决策内容和截止日期。
2. **建议方案**：只给出一个主建议。
3. **为什么是现在**：触发因素、紧迫性和延迟成本。
4. **证据**：带来源的事实、日期和置信度。
5. **备选方案**：主方案、替代方案和不行动方案。
6. **经济性**：适用时说明投资、现金、回报、下行风险和敏感性。
7. **战略匹配度**：与分销业务、东南亚、自研硬件和 AI 转型的关系。
8. **异议与分歧**：顾问之间的实质性不同意见。
9. **红队结论**：最强反对理由和失败条件。
10. **合规与审批门**：必须经过的人工角色以及禁止自动执行的动作。
11. **执行方案**：负责人、里程碑、衡量指标和复盘日期。
12. **止损条件**：触发暂停、反转或重新评估的条件。

主简报应支持 CEO 在 3 分钟内完成阅读。支撑附件可以更长。

### 11.1 Manifest 校验规则

出现以下任一情况时，必须在修改任何 Profile 数据之前失败：

- `kind` 不是 `hermes-profile-team`；
- `version` 不是 `1`；
- root 模板目录不存在；
- 成员标识重复；
- 成员标识不是合法 Hermes Profile ID；
- 被引用的成员模板目录不存在；
- root Profile 不是 `default`；
- 编排引擎不是 `kanban`；
- 共享上下文路径逃逸出实例的 Hermes Home。

## 13. 脚本设计

### 13.1 `scripts/create-instance.sh`

现有命令格式保持不变：

```bash
bash scripts/create-instance.sh <instance> <webui_port> <expert>
```

创建基础实例后，继续调用 `inject-expert.sh`。不得在该脚本内重复实现团队专用逻辑。

### 13.2 `scripts/inject-expert.sh`

调整后的行为：

- 当 `expert-templates/<expert>/team.yaml` 不存在时，原单专家流程完全不变；
- 当 `team.yaml` 存在时，调用 `scripts/inject-expert-team.sh <instance> <expert>`；
- 保留当前配置备份行为；
- Manifest 校验失败时不得部分写入团队文件。

### 13.3 `scripts/inject-expert-team.sh`

职责：

1. 校验团队 Manifest。
2. 为已有 root 和命名 Profile 的身份文件创建带时间戳备份。
3. 把 `expert-templates/base` 应用到 root Profile。
4. 把团队 root 模板覆盖到 root Profile。
5. 按标准 Hermes Profile 目录结构创建全部命名 Profile。
6. 以 Profile 相对路径把 `expert-templates/base` 应用到每个命名 Profile。
7. 应用对应成员模板。
8. 把已经审核的共享上下文复制到 `/data/hermes/team-shared`。
9. 把共享上下文权限设置为运行时可读、不可写。
10. 把团队 Skills 安装到 root Profile。
11. 把 Agency Agents Router 安装或复制到 Manifest 指定的 Profile。
12. 生成 root 和命名 Profile 的运行时配置。
13. 生成唯一 Hindsight Bank ID。
14. 在 root Profile 中配置 Kanban。
15. 把解析后的运行时 Team Manifest 写入 `/data/hermes/team.yaml`。
16. 执行结构验证，失败时返回非零退出码。

### 13.4 `scripts/lib/team_manifest.py`

该模块独占 Manifest 解析和校验职责。Shell 脚本必须消费它输出的 JSON，不得使用 `grep`、`sed` 或 `awk` 直接解析 YAML。

必须支持：

```text
validate <team.yaml>
resolve <team.yaml> --instance <instance>
list-members <team.yaml>
```

输出必须是稳定、可机器读取的 JSON；错误信息必须明确指出字段和原因。

### 13.5 `scripts/patch-config-runtime.sh`

在保持现有单参数调用兼容的同时，增加可选参数：

```text
--profile-home
--workspace-path
--vault-path
--gbrain-home
--hindsight-bank-id
```

root 默认路径仍然是 `/data/hermes/...`；命名 Profile 使用 Profile 相对路径。

### 13.6 `scripts/lib/patch_config_runtime.py`

运行时 Patch 生成器必须接受显式路径，并增加以下配置：

```yaml
kanban:
  dispatch_in_gateway: true
  dispatch_interval_seconds: 30

delegation:
  max_concurrent_children: 3
  max_spawn_depth: 1
  orchestrator_enabled: true
  inherit_mcp_toolsets: false
```

`kanban` 配置只允许 root Profile 启用。命名 Profile 在 Dispatcher 启动为 Worker 时可使用 Kanban Worker Tools，但不得运行独立 Dispatcher。

### 13.7 `scripts/check-expert-team.sh`

Doctor 脚本必须校验：

- root 和预期的 7 个命名 Profile 均存在；
- 每个 Profile 都包含 `SOUL.md`、`config.yaml`、`memories` 和 `workspace`；
- 所有 Hindsight Bank ID 唯一；
- 所有 Workspace 和 Vault 路径均位于预期 Profile Home 内；
- root Kanban Dispatcher 已启用；
- 命名 Profile 未启用独立 Dispatcher；
- Agency Agents Router 存在于 Manifest 指定的 Profile；
- 共享上下文文件存在且运行时不可写；
- 容器运行时 WebUI 和 Gateway 健康检查通过；
- `hermes profile list` 包含所有命名成员；
- `hermes kanban --help` 可用；
- 任何命名 Profile 都没有独立 Gateway PID 或端口配置。

## 14. 运行时配置规则

### 14.1 root Profile 路径

```text
HERMES_HOME=/data/hermes
workspace=/data/hermes/workspace
vault=/data/hermes/obsidian-vault
gbrain=/data/hermes/gbrain
hindsight bank=hermes-<instance>-default
```

### 14.2 命名 Profile 路径

对于 Profile `<member>`：

```text
profile home=/data/hermes/profiles/<member>
workspace=/data/hermes/profiles/<member>/workspace
vault=/data/hermes/profiles/<member>/obsidian-vault
gbrain=/data/hermes/profiles/<member>/gbrain
hindsight bank=hermes-<instance>-<member>
```

命名 Profile 在创建时继承解析后的 root Model 与 Provider 配置，但保留独立的 Runtime、Memory 和 Identity 配置。

### 14.3 共享上下文

所有 Profile 均可读取：

```text
/data/hermes/team-shared
```

该目录只允许保存已经审核的组织事实。原始上传文件、凭据、交易细节、未公开董事会资料和未经审核的结论不得写入该目录。

共享上下文更新只能通过模板维护或未来经过审批的知识治理流程完成，普通顾问任务不得修改。

## 15. 记忆模型

### 15.1 共享知识

共享静态上下文包括：

- 公司身份与上市公司状态；
- 业务组合与区域重点；
- CEO 背景与决策偏好；

- 决策评价标准；
- 授权数据源目录；
- 团队角色和职责边界。

### 15.2 Profile 隔离记忆

每个永久顾问拥有独立的：

- Hindsight Bank；
- `memories/MEMORY.md`；
- `memories/USER.md` 中的角色化用户理解；
- Sessions；
- Workspace；
- 专业规律、经验和纠错记录。

任何 Profile 不得直接写入其他 Profile 的 Memory 或 Sessions。

### 15.3 决策记录

正式决策日志保存在 root 控制路径：

```text
/data/hermes/workspace/reports/ceo/decisions
/data/hermes/obsidian-vault/60-Reports/CEO-Decisions
```

只有经过审核的 Markdown 摘要可归档到 Obsidian。敏感原始资料必须保留在 Workspace。

- 用于 root 编排辅助的 Chief of Staff Pattern；
- Chief Financial Officer；
- Trend Researcher；
- Account Strategist；

## 17. 安全与治理

### 17.1 保留动作

系统不得自动执行：

- 审批或执行投资；
- 发布交易所公告或投资者沟通；
- 发送外部消息；
- 承诺价格、库存、交期、信用或合同条款；
- 给出最终法律结论；
- 作出人事决策；
- 修改生产 EBS、财务、CRM 或运营记录；
- 泄露董事会、客户、员工或交易机密数据。

### 17.2 审批行为

当任务涉及保留动作时，输出必须明确：

- 建议执行的动作；
- 支撑证据；
- 尚未解决的风险；
- 必须审批的角色；
- 哪个具体动作仍未执行。

### 17.3 来源处理

D2–D4 简报中的每个重大结论必须标记为以下之一：

```text
已验证事实
有依据的推断
假设
建议
未知 / 需要证据
```

当重大数字没有来源或内部不一致时，`compliance-evidence` 必须阻止简报以事实形式定稿。

## 18. 故障处理

### 18.1 创建失败

团队创建使用实例 Backup 区域中的 Staging 目录。只有 Manifest 校验和模板暂存全部成功后，才能替换现有线上 Profile 文件。

失败时必须：

- 返回非零退出码；
- 输出失败的 Profile 和文件；
- 保持原线上结构不变；
- 保留 Staging 目录供诊断；
- 不得留下被标记为 Active 的半成品 `team.yaml`。

### 18.2 Hermes 能力缺失

启动验收前，Doctor 脚本必须验证：

```text
hermes profile list
hermes kanban --help
```

如果 Kanban 不可用，则该团队运行时必须判定为不受支持。不得静默地把永久 Profile 协作降级为匿名 `delegate_task` 调用。

### 18.3 Worker 失败

Kanban 任务必须使用 Block、Retry 和 Comment 语义。永久 Profile 的失败任务必须保留审计记录，并可重新分配或解除阻塞。root Profile 必须报告阻塞状态，不得伪造顾问已经完成的意见。

### 18.4 动态专家失败

动态专家失败时把错误返回调用 Profile。调用方可以：

- 使用更窄的任务重试一次；
- 选择另一个动态专家；
- 继续流程，但必须明确标记缺失的专业视角。

- Agency Agents Router 已安装；

分别创建 `writer`、`finance` 和 `sale` 实例，确认生成目录和启动行为与改造前一致。

### 21.3 幂等重复注入

连续执行两次团队注入。第二次必须：

- 保留有效的现有 Model/Provider 配置；
- 创建新的时间戳备份；
- 不重复创建 Profile、Skill 或 Plugin；

- 创建了相关顾问任务；

### 21.6 重启恢复

在多 Profile Kanban 工作流执行中重启容器，确认持久任务仍然存在，未完成任务不会被表示为已完成。

### 21.7 动态专家隔离

委派一个 Trend Researcher 任务，确认子 Agent：

- 只获得有边界的任务上下文；
- 不创建永久 Profile 目录；
- 无法写入共享 Memory。

## 24. 最终实施基线

最终实施基线固定为：

```text
1 个 Docker 容器
1 个 root/default Chief of Staff Profile
7 个永久顾问 / 审查 Profile
1 个 Hermes Kanban 协作平面
1 个 Agency Agents 动态专家池
1 个只读公司共享上下文目录
1 个统一面向 CEO 的 WebUI 和 Gateway
```

任何出现以下情况的实现，均不符合本规格：

- 把 7 个永久顾问合并进一个 Prompt；
- 只用 `delegate_task` 替代 Kanban 和永久 Profile 协作；
- 把每个顾问部署成独立容器；
- 为命名 Profile 分配单独 WebUI 或 Gateway；
- 多个 Profile 共用同一个 Hindsight Bank、Workspace 或长期记忆；
- 未经红队、合规审查和人工审批直接执行 D3/D4 保留动作。
